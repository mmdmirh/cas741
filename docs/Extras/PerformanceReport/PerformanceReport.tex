\section{Introduction}

\progname{} is a real-time pose-based exercise feedback tool. The
performance requirement is not a single number; the system just has to
feel responsive while drawing an AR overlay on the live webcam feed.
This report makes that concrete. It lists the aspects of performance
that matter, the way they were measured, the results, and the two
changes during the project that improved performance. Some of this
material is already in the VnV Report. It is repeated here so a
performance-focused reader has everything in one place.

\section{Performance Aspects}

In priority order, the aspects that matter for \progname{} are:

\begin{enumerate}
  \item Per-frame end-to-end latency. Time from a webcam frame
    arriving at the browser to the overlay and rep counter for that
    frame being rendered. This is what the user sees as ``laggy''.
  \item Sustained throughput, measured as frames per second (FPS)
    under continuous operation. The target is at least 24 FPS, which
    is where live video still feels smooth.
  \item Angle-signal stability, reported as
    $\overline{|\Delta\theta|}$ (defined in VnV Report \S4.1). This is
    mostly a quality signal, but it also limits how much smoothing M8
    has to do, which feeds back into responsiveness.
  \item Test-suite runtime, so that local iteration stays fast.
\end{enumerate}

Two things are out of scope and were not measured: resident memory of
the backend process, and GPU utilisation, since the production path
runs on CPU only.

\section{Measurement Methodology}

\subsection{Hardware and software under test}

Measurements were taken on the author's macOS workstation, Apple
Silicon, using the \texttt{mediapipe-silicon} wheel. The backend runs
on Python~3.9.6 with the package versions pinned in
\texttt{src/backend/requirements.txt}; the frontend runs on Node.js
via Vite. No machine-specific tuning was used and GPU acceleration was
not enabled, so the numbers here should be read as a baseline for a
recent laptop.

\subsection{Benchmark drivers}

Three measurement tools were used:

\begin{itemize}
  \item An offline dynamic benchmark script that replays a recorded
    video dataset through each of the three pose backends (MediaPipe
    2D, MediaPipe 3D, MoveNet 3D) and records per-frame latency and
    the resulting joint-angle time series. The dataset contains short
    squat and bicep-curl clips at two camera pitches (eye-level,
    $45^{\circ}$-down) and five orientations (front, front-$45^{\circ}$,
    side, back-$45^{\circ}$, back).
  \item A live FPS counter in the frontend. It samples
    \texttt{performance.now()} inside the WebSocket render loop and
    reports an exponentially smoothed FPS value. This is what was used
    to confirm the throughput target during the POC and the EXPO.
  \item \texttt{make test} wall time, which covers all 11 tests from
    VnV Report \S6.
\end{itemize}

\subsection{Metrics}

\begin{itemize}
  \item Latency, in ms: average per-frame processing time from the
    dynamic benchmark script.
  \item Stability:
    $\overline{|\Delta\theta|}
      = \frac{1}{N{-}1}\sum_{i=1}^{N-1}|\theta_i - \theta_{i-1}|$
    on the computed joint-angle signal. Lower means more stable.
  \item Throughput (FPS): the inverse of end-to-end latency under
    sustained load.
\end{itemize}

MediaPipe 2D is the best backend for this application on every metric
that matters, except on elbow stability, where MediaPipe 3D is better
by about $1.5^\circ$. The 2D backend was chosen as the production
default.

\subsection{Throughput}

An average of $\sim 39$~ms per frame gives a ceiling of about
$25.6$~FPS on the production backend. During the POC (2026-03-05) and
the EXPO, the live FPS counter stayed at $\ge 24$~FPS throughout each
rep set, which is within the target.

\subsection{Test-suite runtime}

\texttt{make test} finishes in under 5 seconds locally for all 11
tests. That is short enough to keep local iteration fast.

\section{Performance Improvements}

Two changes over the project improved performance relative to the
CAS~772 monolithic prototype that \progname{} was refactored from.

\subsection{Backend selection (M4)}

The CAS~772 prototype ran only MediaPipe 3D (world landmarks enabled).
Switching to MediaPipe 2D for production reduced per-frame latency
from $\sim 41$~ms to $\sim 39$~ms, and knee-angle stability went from
$\sim 1.2^\circ$ to $\sim 0.7^\circ$. The change needed only a
configuration switch behind the M4 (\texttt{m4\_pose\_tracking.py})
interface, because M4 hides the backend. That is the modular
decomposition paying off in practice.

\subsection{Kalman smoothing (M8)}

The raw per-frame angle signal has a per-sample standard deviation of
roughly $5^{\circ}$ on the T\_M8 synthetic noise case. After the
Kalman smoother is applied, the post-transient standard deviation is
smaller than the raw standard deviation in every run. The practical
effect is that a single noisy frame no longer fools the state machine
into counting a false rep.

\section{Bottleneck Analysis}

Under the production configuration (MediaPipe 2D plus Kalman smoothing
plus the vectorised angle computation), most of the per-frame time is
spent inside the pose backend itself. About $35$--$37$~ms of the
$\sim 39$~ms budget is inside the MediaPipe wheel. The analytical
pipeline (vector math in M5 plus the FSM step in M6) adds roughly
$2$~ms. Optimising the analytical pipeline further would not help much.
The next place to look is the pose backend itself: for example,
quantisation, the MediaPipe GPU-delegate path on supported hardware,
or a smaller model like MoveNet Lightning if a small loss of
stability is acceptable.

\section{Conclusion}

The production configuration meets the performance requirements for
\progname{}. Sustained throughput of $\ge 24$~FPS and knee-angle
stability of $\sim 0.7^\circ$ are both good enough for the user
experience the system is aiming for. The remaining risk is not a
performance problem. It is the absence of a physical goniometer
validation of the pose backend against an independent ground truth,
which is listed as open work in VnV Report \S4.1.
